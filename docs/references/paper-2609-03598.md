# RASER paper assessment

**Paper:** *RASER: Resilient Agent Scheduling and Execution Runtime for HPC Clusters*, Sima Attar-Khorasani, Matthias Lieber, and Siavash Ghiasvand. arXiv preprint, submitted 3 September 2026; reviewed version **2609.03598v1**. [Versioned record](https://arxiv.org/abs/2609.03598v1).

## What the paper establishes

[Section 3](https://arxiv.org/html/2609.03598v1#S3) describes cluster-side agent execution using Slurm arrays, filesystem task claiming, checkpoints/requeue, and Apptainer environments. [Section 4](https://arxiv.org/html/2609.03598v1#S4) reports 38.8% shorter makespan for 60 SWE-bench-Lite tasks; comparison memory allocations differ. It exercises SIGTERM recovery without quantifying lost work. [Section 5](https://arxiv.org/html/2609.03598v1#S5) identifies GPU benchmarking as future work; evaluation was CPU-only.

These are authors' reported findings, not results reproduced by this project. They do not establish our credential-protection or budget guarantees.

The paper links [RASER's primary GitLab repository](https://gitlab.hrz.tu-chemnitz.de/siat527e--tu-dresden.de/raser). Its landing page was reachable; source/license contents were not audited or executed. No code is incorporated by this assessment.

## Our architectural interpretation

RASER is a potential **workload inside an authorized allocation**, rather than a substitute for our broker. Our proposed adoption boundary is a separately packaged runtime submitted as an ordinary job. Project authorization, human approval, resource reservations, SSH keys, and accounting remain outside that runtime. Consequently it has no authority to increase its own budget, extend walltime, or directly obtain broker credentials.

Keep the first release focused on bounded single-node jobs. Arrays, automatic requeue, and persistent agent ensembles would expand both admission and accounting semantics. Enable them only after explicit design review and the corresponding tests. A useful runtime should also benefit ordinary compute workloads; adopting an agent framework must not become a prerequisite for submitting Python.

We propose immutable, digest-verified runtime artifacts inside each reviewed package. Runtime upgrades or instrumentation changes require a new package version. Any model/API credential used by an optional in-cluster agent would be narrowly scoped, short-lived where possible, and distinct from SSH, human approval, project administration, and worker credentials. Neither a private workspace nor a container name proves isolation between processes sharing an OS identity.

## Proposed acceptance consequences

1. **Task ownership:** simulate a slow worker that misses heartbeats but remains alive. After reassignment, ownership epochs must fence stale writes. A lease timeout alone cannot establish that the original process stopped. Irreversible external actions need idempotency or operator reconciliation; do not promise exactly-once effects.
2. **Recovery:** kill a process during checkpoint creation and restoration. Require atomic checkpoint publication, schema/version validation, safe archive extraction, and explicit handling of corrupt or incompatible state. Restore cannot replay an external side effect silently. A workspace archive alone is not proof that arbitrary interpreter/GPU/network state is resumable.
3. **Bounded execution:** restart, retry, checkpoint, idle time, and requeue all consume authorized allocations. Test aggregate resource/time ceilings, terminal cancellation, maximum restarts, and exhausted allowances. A runtime must terminate rather than maintain an unlimited respawn loop.
4. **Site validation:** test actual shared-filesystem locking/visibility and signal grace periods before enabling a runtime. Benchmark matched hardware, memory limits, workloads, fault schedules, and total allocated resource-seconds. Measure duplicate execution and lost work as well as makespan. A local filesystem fixture cannot establish distributed-filesystem behavior.

These are our proposed requirements, not deficiencies experimentally demonstrated in RASER. See [the testing guide](../testing.md) for current evidence and the [roadmap](../roadmap.md) for future scope. Reuse remains conditional on source/license review, reproducible integration, and site acceptance.
